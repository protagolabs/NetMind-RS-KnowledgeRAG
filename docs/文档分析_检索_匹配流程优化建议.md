# 文档分析、检索与匹配流程优化建议

- 项目：NetMind-RS-KnowledgeRAG
- 目标：提升正确性、稳定性、可维护性与检索/回答质量
- 范围：围绕“文档分析 → 索引 → 检索 → 匹配/重排 → 上下文压缩 → 生成/引用”的流程优化建议

## 结论概览

- 当前总体思路正确，但在分块策略、表示（embedding/insights）、检索融合、相关性复核、上下文组装与质控上有显著优化空间。
- 采用“更好的分块 + 多向量精简 + 混合检索 + 强力重排（cross‑encoder）+ 上下文压缩”的组合，可显著提升相关性与可用性，同时降低 LLM 成本与延迟。

## 现状简述（基于仓库代码与文档）

- 分析：MarkdownHeader 分块；LLM 生成文档/片段的 summary、insights、keywords，并对其进行向量化。
- 索引：MySQL 全文索引（summary、doc_markdown_content）；Milvus 存储文档/chunk 的 embedding（含多条 insights 向量）。
- 检索：先文档（向量/全文）再 chunk（向量/全文/insights 向量/文本），结果合并并排序。
- 匹配：用 LLM 对文档与片段做相关性 gating（score≥20 视为相关）。
- 生成：已有“规划/写作”提示词雏形。

## 主要痛点

- 分块与上下文边界：标题分割 + 定长窗口易切断语义；缺少跨段落合并与相邻扩展策略。
- 表示冗余与成本：对 summary、keywords、每条 insight 进行向量化，成本高且信息冗余；不同 schema 的维度/度量不统一。
- 检索融合浅：简单“合并 + 取最大分”的启发式融合，缺少强力重排与去重策略；中文全文检索依赖 MySQL Fulltext，效果有限。
- 匹配复核成本高：用 LLM 做 gating 成本大；阈值常数（20）未校准；缺少可学习的快速 reranker 做前置过滤。
- 证据覆盖：仅取命中 chunk，缺少“相邻扩展 + 句级压缩”，易丢关键信息或引入噪声。
- 评估缺位：无系统化离线评测（Recall@n、MRR、nDCG）与线上 A/B；难以量化改进。

## 优化路线（五层）

### 1) 分块与预处理

- 层次化分块：结构优先 + 语义辅助。以标题层级聚合段落，二次用句子边界与滑动窗口（200–400 tokens，overlap 10–20%）抹平边界。
- 边界修复：为每个 chunk 记录“相邻扩展窗口”（前后各一段）以备下游拼接。
- 去重归一：对高相似 chunk（simhash/minhash 或 embedding 相似度）做合并去重，降低冗余与索引成本。

### 2) 表示与索引

- 多向量表示（MVR）精简：
  - 每个 chunk 保留 1 个 summary 向量 + 3–8 条“检索导向 insights”（短句，面向检索与问法）。
  - 文档层保留 1–2 条聚合向量（摘要/核心要点）。
- 统一维度与度量：全链路一致（如 768/1024/1536，统一 L2 或 COSINE）；Milvus index 参数（nlist、nprobe/ef）入配置。
- 关键词索引升级：中文全文检索优先引入专用引擎（Elasticsearch/Meilisearch/Tantivy/BM25+中文分词），替代/增强 MySQL Fulltext；保留“BM25+向量”混合检索。
- 结果缓存：embedding/LLM 输出按文本哈希缓存，显著降低调用成本。

### 3) 检索与融合

- 意图路由：
  - 短/符号化查询 → BM25 权重高；
  - 长/概念性查询 → 向量权重高；
  - 带实体/版本/时间 → 元数据过滤优先；
  - 策略写入配置，便于调参。
- 两阶段检索：
  - 初筛（doc 或 chunk 直达） → 重排（cross‑encoder，如 bge‑reranker‑large/mini）。
  - 分离“召回”和“排序”，本层不使用 LLM。
- 学习式融合（可选）：
  - 将向量相似度、BM25 分、位置/结构特征、query‑doc/chunk 交互等输入轻模型（LR/GBDT/小 MLP）学习融合权重。
  - 无标注时先用启发式线性加权，优于“取最大分”。
- 去重与聚合：按 doc collapse（同文档保留高分 Top‑k）；多源 chunk 合并时按“最高融合分 + 多源证据”排序。

### 4) 相关性复核与上下文压缩

- 先强力重排，再轻量 LLM gating（小上下文、低温度、简短依据）；或以跨编码器分数阈值直接替代 LLM gating，仅在最终证据一致性处使用 LLM。
- 上下文压缩：对入模 chunks 做句级评分（可用小模型或 TextRank），保留关键句并附段落标识；控制 token ≈ 原文的 1/2–1/3。
- 相邻扩展：对高分 chunk 自动携带前/后一两句，缓解截断问题。

### 5) 生成与引用

- 引用稳定：保留 chunk_id、section_path、行号/句号索引；生成时强制句级引用。
- 一致性检查：写作后用小提示词做“反事实/不在证据中”的二次剔除。
- 输出结构化：按问法输出 TL;DR + 证据要点 + 细节展开 + 引用清单。

## 具体落地建议

### 分块

- 规则：标题层级 → 段落聚合 → 句子边界 → 窗口（200–400 tokens）+ 10–20% overlap。
- 产物：`chunk_text`、`section_path`、`seq_no`、`token_count`、`neighbors`（prev/next）。

### 表示

- 每 chunk：1 个 summary embedding + 3–8 个检索导向 insight embedding（短句）。
- 文档层：1–2 个聚合 embedding。
- 统一 embedding 维度/度量 + Milvus 索引参数；embedding 模型统一（如 bge‑m3/eba 或 OpenAI text‑embedding‑3 家族，二选一）。

### 检索

- 初筛：BM25（中文分词）Top‑N 与向量 Top‑M 并行，合并后保留 Top‑K（N/M/K 可调）。
- 重排：cross‑encoder（bge‑reranker‑large/mini）将 Top‑K 排为 Top‑L（如 50→15）。
- 合并：按 doc collapse；每文档保留 1–3 个代表 chunk；按融合分排序。

### 匹配与压缩

- 替代 LLM gating：以 cross‑encoder 分数阈值为主；必要时再用轻提示词复核极少数边界样本。
- 上下文压缩：对最终 chunks 进行句级压缩（保留 60–70% token），确保关键信息；必要时携带相邻句。

### 评估与监控

- 构建最小标注集（20–50 条 query→gold docs/chunks），评估 Recall@5/10、MRR、nDCG。
- 线上采样人工评估（评分维度：相关性/覆盖/事实性/冗余度/引用质量），记录可解释样例。
- 监控：命中率、重排提升、平均上下文 token、回答长度、引用率、延迟分解（召回/重排/LLM）。

## 快速收益（优先级）

### 高（1–3 天）

- 改良分块（句界 + 窗口 + 相邻扩展）与去重。
- 引入 cross‑encoder 重排，替代 LLM gating 作为主流程。
- 统一 embedding 维度/度量与 Milvus 索引参数；将多向量精简为“少而精”的 insights。

### 中（1–2 周）

- 引入/增强中文 BM25 引擎（ES/Meilisearch/Tantivy）。
- 意图路由与融合权重调参；构建离线评测集与 A/B 测试。
- 上下文压缩与引用稳定化（句级引用链路）。

### 长期（>2 周）

- 轻量学习式融合（LR/GBDT/小 MLP）替代静态加权。
- 域内蒸馏/微调检索器与重排器；多模态/表格场景特化。

## 风险与权衡

- 成本：多向量与全量 insights 向量化成本高 → 改为“精挑少量检索导向 insights”+ 缓存。
- 延迟：cross‑encoder 重排引入耗时 → 通过 Top‑N 限制与 batch 优化控制在 50–150ms 级别。
- 复杂度：引入 BM25 引擎与学习式融合增加系统复杂度 → 先从可配置混合检索+重排起步，渐进演进。

## 附：与现状的关键差异（对照）

- 现状：LLM 相关性 gating 占比较重 → 建议：重排（cross‑encoder）为主，LLM 只做一致性/引用审校。
- 现状：对所有 insights 全量向量化 → 建议：精简为“检索导向”的少量高质量短句，减少冗余与成本。
- 现状：MySQL Fulltext 做中文全文检索 → 建议：引入专业 BM25 引擎与中文分词，效果显著更稳。
- 现状：简单分数合并 → 建议：线性加权/学习式融合 + 去重与 doc collapse，排序更稳健。
